# Rehearsal: release v2.0, roll back to v1.0.0

The rehearsal for spec 019 (slice 3.11, S7.1, SC-002), run on 2026-11-06 before v2.0 reached main or the live channel. It ran on preview channels of the `bradthome` site only, with the scripts the release and rollback workflows run, as Brad's own login. That needed no grant on `release-deployer`, so nothing in Google Cloud changed. It's shaped like slice 2.6's ([rehearsal](rehearsal.md)).

## Setup

- The candidate was the branch's build at `2494ea8`, made in the pinned Playwright container by `pnpm test:visual`, with the résumé PDFs printed and `pnpm csp --check` passing. It was deployed with the repo's `firebase.json` to channel `v2-rc` as version `bbe86b09b6b2b6aa`, which is also the preview Brad opened on a phone.
- Releases went to channel `rehearsal-v2`, created for the rehearsal, expiring a day later.
- v1.0.0, which bradthome.com serves, is version `0749adf539329b20` (`pnpm release:status`).

## The pre-release check

Against bradthome.com, with only the home's words allowed to change:

```text
$ pnpm release:check --candidate https://bradthome--v2-rc-41m2iq9k.web.app --home-words-may-change
– check  Hosting sets its own HSTS on bradthome--v2-rc-41m2iq9k.web.app, so the check reads firebase.json's: max-age=63072000; includeSubDomains
– check  words differ on /: live has “Brad Thome Brad Thome GitHub LinkedIn Brad Thome Senior full-stack”, candidate has “Brad Thome Skip to the content Brad Thome Hopper Experience” (this run allows it)
✓ check  https://bradthome--v2-rc-41m2iq9k.web.app serves every URL, redirect, security header and word that https://bradthome.com does (11 URLs, 2 pages' words)
```

The essay's words matched, with its renamed title allowed ([D163](../decisions/0163-the-essays-title-drops-one-person.md)), the policy added only Umami's one `connect-src` host ([D159](../decisions/0159-spec-003-allows-umamis-api-host.md)), and `/v2` answered 301 to `/` ([D162](../decisions/0162-the-new-home-moves-to-the-root-and-v2-redirects-there.md)).

## What the rehearsal found

The first run of the pre-release check against `v2-rc` failed every page on Strict-Transport-Security: Hosting sends its own one-year value on `*.web.app` in place of `firebase.json`'s ([D99](../decisions/0099-the-preview-comments-with-pull-requests-write-and-accepts-hostings-hsts.md)), and live bradthome.com now sends `firebase.json`'s two years. v1.0.0's release passed only because live was v0 then. Every later release's stage job, which checks the `release` channel on `web.app`, would have failed the same way. The check now reads `firebase.json`'s value for a candidate on Hosting's own domains, says so, and still fails a weaker one (spec 019's S5.6).
